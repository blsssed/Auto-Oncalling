# 设计：诊断过程可视化打磨

## 决策

### 1. 证据按 kind 分组，顺序固定

前端只使用后端已返回的 `chain.evidence`，按 `log`、`metric`、`alert`、`ticket`、`knowledge_reference` 的固定顺序分组，未知类型排在末尾并直接显示原始 kind。分组计数来自数组长度，不补造缺失类型。

### 2. 引用标记只信 reportEvidenceLinks

“报告引用”标记以 `chain.reportEvidenceLinks` 的 `evidenceId` 集合为准。报告自身的 `evidenceIds` 不作为前端推断来源，避免出现持久化链接缺失时误标。被引用证据所在分组默认展开，其余分组默认收起；首个分组保持展开以便查看。

### 3. 关键词高亮使用文本切片

摘要先按正则切成 `{ text, hit }` 片段，再用 `<mark>` 渲染命中片段。整个流程不拼接 HTML、不使用 `v-html`，因此证据文本中的标记不会被当作脚本执行。保留原始 `payload` 不展示的既有边界。

### 4. 保留引用锚点

每个证据条目仍使用 `id="evidence-<id>"` 和 `tabindex="-1"`，报告引用点击继续走 `locateEvidence`。由于被引用证据所在分组默认展开，嵌套 `<details>` 不会阻断跳转后的可见性。

### 5. 时间线只补充真实元数据

实时时间线新增的计数来自当前事件数组；知识引用详情仅展示契约中的 `sourceType`、`score` 和截断 `excerpt`。没有数据时不显示占位值。

## 风险

- 证据摘要文本长度可能较大；沿用原有的可换行文本样式，并仅展示 `summary`，不展示 `payload`。
- 引用标记依赖后端链接数据；链接缺失时宁可不标记，也不根据报告文本猜测。
