# 设计：告警自动诊断

## 决策

### 1. 用快照差异识别“新告警”

轮询在 `replace_snapshot` 前读取上一份 `active_alerts` 快照，只有 id 不在旧快照中的告警才可能触发自动诊断。这样服务重启后已有告警不会被重复诊断，告警消失后再次出现才视为新事件。

替代方案是维护单独的“已诊断”表；代价是需要额外迁移和清理，且与现有快照语义重复，因此不采用。

### 2. owner 由配置邮箱解析

告警是全局数据，诊断必须归属某个用户。配置只接受已注册用户邮箱，轮询时通过认证仓储解析；找不到用户时记录事件并跳过，不创建任何无主数据。

### 3. 去重与节流

- 同一告警在 `dedupeWindowSeconds` 内已有诊断任务时跳过，无论其最终状态，避免失败任务造成诊断风暴。
- 每轮最多创建 `maxPerPoll` 个任务。
- 级别过滤使用小写、去空格的精确匹配，默认仅 `critical`。

### 4. 复用 durable 诊断任务与 job

自动诊断与 `POST /aiops/diagnostics` 使用相同的任务状态、`aiops_diagnosis` job kind、超时和重试语义；job payload 额外记录 `alertId` 便于关联。自动诊断是轮询的副作用，失败只记录日志与事件，不阻塞下一次轮询入队。

### 5. 告警状态按用户作用域附加

告警本身全局共享，但诊断任务按 owner 隔离。REST/SSE 载荷在序列化时按当前用户查询其诊断任务并附加 `diagnosticId` 与 `diagnosisStatus`，不会向其他用户泄露任务归属。

## 风险

- 轮询任务每轮多一次快照读取；数据量为当前活跃告警规模，可接受。
- 自动诊断任务同样会消耗 LLM 与工具配额，因此默认关闭，并通过级别、去重窗口和每轮上限约束。
